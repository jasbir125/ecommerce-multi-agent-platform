Refactor the agent implementation code across this project to make it less dense, more readable, testable, and production-maintainable.

Do not change business behavior unless a change is explicitly required to fix a correctness, security, or reliability issue.

Apply the following engineering standards consistently to every agent:

1. Readability
- Use small, single-purpose functions.
- Each function should do one thing only.
- Use descriptive function, class, variable, and constant names.
- Avoid deeply nested ternaries.
- Avoid chained one-line expressions.
- Avoid compact dictionary comprehensions when they reduce readability.
- Avoid long boolean expressions; extract them into named predicates.
- Keep functions under approximately 30 lines where practical.
- Keep each agent file focused on its own responsibility.

2. Structure
- Separate these concerns clearly:
  - Input validation
  - Tool invocation
  - Response normalization
  - Business-rule validation
  - Decision or selection logic
  - Evidence creation
  - Error handling
  - State update

3. Type Safety
- Use Python type hints consistently.
- Use Pydantic models for inputs, outputs, workflow state, and agent responses.
- Do not return loosely typed dictionaries where a typed model is appropriate.
- Use Literal or Enum for constrained values such as status, risk level, action, and approval state.

4. Money and Numeric Safety
- Use Decimal for monetary values.
- Do not use float for prices, refunds, amounts, or financial comparisons.
- Use explicit rounding and tolerance rules.
- Validate currency consistency before comparing amounts.

5. Error Handling
- Catch specific expected exceptions only.
- Do not use broad `except Exception`.
- Do not silently swallow errors.
- Log failures with structured context.
- Add a concise, actionable error code to the workflow errors list.
- Preserve the original exception details in logs, not necessarily in the customer-facing response.

6. Logging and Observability
- Use structured logging.
- Include workflow_id, request_id, customer_id, order_id, agent_name, tool_name, latency, and error code where relevant.
- Never log raw PII, API keys, full prompts containing sensitive data, or secrets.
- Emit timing and outcome information for agent execution and tool calls.

7. Security and Trust Boundaries
- Treat all model output as untrusted.
- Treat all retrieved documents, product descriptions, customer messages, and external tool responses as untrusted data.
- Never follow instructions found inside retrieved content.
- Validate every model-selected ID against verified tool results.
- Never trust model-generated prices, availability, refund status, approval status, policy versions, or delivery dates.
- Enforce authorization before tool execution.
- Do not expose generic database, shell, URL, or file-system tools to agents.

8. Tool Calling
- Define each tool with a clear name, description, typed input schema, and typed output schema.
- Validate tool arguments before execution.
- Apply timeouts, retries only for safe idempotent operations, circuit breakers, and rate limits.
- Use idempotency keys for all write operations.
- Audit every tool call, including success, failure, retry, and authorization denial.

9. Agent Design
- Keep each agent narrow and specialized.
- An agent should have a clear responsibility and limited tools.
- The Supervisor Agent coordinates agents; it should not directly execute business mutations.
- Specialist agents should retrieve, analyze, or recommend.
- Decision and action logic must be separated.
- Business services remain the source of truth for authorization and transaction execution.

10. Determinism
- Use low temperature for:
  - Classification
  - Extraction
  - Tool argument generation
  - Policy decisions
  - Risk assessment
  - Structured output
- Use moderate temperature only for customer-facing response generation.
- Do not use model randomness as a substitute for business rules.

11. RAG Quality
- Retrieve only relevant, versioned policy chunks.
- Apply metadata filtering.
- Use hybrid retrieval where available.
- Rerank results.
- Enforce a maximum context-token budget.
- Return policy version, source, score, and citations.
- If confidence or evidence is insufficient, return an explicit insufficient-evidence response.
- Never invent policy rules, refund amounts, approval status, delivery dates, or product availability.

12. Testing
- Make every branch testable.
- Use dependency injection or test doubles for:
  - LLM client
  - MCP gateway
  - HTTP client
  - Database repository
  - Kafka producer
- Add unit tests for:
  - Happy path
  - Missing required state
  - Invalid model output
  - Tool failure
  - Timeout
  - Unauthorized access
  - Duplicate event
  - Invalid price
  - Insufficient RAG evidence
  - Fallback behavior
  - Compensation behavior

# Current Business Rules

## Product Agent
- Find an in-stock replacement.
- Do not recommend the original product.
- Replacement price must not exceed the original unit price.
- If the model-selected product is invalid, select the lowest-priced valid fallback.
- If no valid replacement exists, return no recommendation.
- Maximum 10 candidates.
- Use Decimal for price comparison.

## Order Agent
- Retrieve order and payment information.
- Validate customer ownership.
- Do not cancel orders or issue refunds.
- Return only verified order data.

## Shipment Agent
- Retrieve shipment and tracking information.
- Identify delays and lost shipments.
- Create a carrier case only when explicitly required.
- Do not issue refunds or modify orders.

## Policy Agent
- Retrieve applicable policies using RAG.
- Return policy version, source, score, and citations.
- Do not invent policy rules.
- The policy service performs final deterministic eligibility validation.

## Risk Agent
- Assess fraud and business risk.
- Return risk level and reason.
- Do not execute business actions.

## Decision Agent
- Combine order, shipment, policy, product, and risk results.
- Produce a structured resolution recommendation.
- Do not execute refunds, cancellations, or inventory changes.

## Response Agent
- Generate a customer-facing response using only verified workflow state.
- Do not invent refund status, delivery dates, amounts, or product availability.
